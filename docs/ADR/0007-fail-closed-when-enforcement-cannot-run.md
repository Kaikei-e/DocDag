# 0007: 検査が実際には走らない経路をすべて失敗に倒す（fail-closed）

## コンテキスト

### 自己コーパスの CI が「0 件の検査」に合格した

DocDag は自分の ADR を CI で検証している。ff973b0 で `docdag.yaml` の `dir:` を `docs/adr` から
`docs/ADR` に変えたが、記録本体は `docs/adr/` に残った。`docs/ADR/` にあったのは `template.md` だけで、
これはファイル名パターンに一致しないため文書として読まれない。結果、`docdag validate` は

```
OK: 0 docs, 0 typed edges, no cycles
```

を出して exit 0 で通った。CI が落ちたのは、その後ろに置いていた `query --binding` の出力を期待値と
突き合わせる手書きのシェル検査がたまたま空文字を拾ったからで、DocDag 自身は何も言っていない。
macOS（大文字小文字を区別しないファイルシステム）では `docs/ADR` が `docs/adr` に解決されるので、
同じ設定がローカルでは通り、Linux の CI でだけ空になる、という OS 依存のすり抜けでもあった。

### 同じ形のすり抜けが他にもあった

コードを静的に追うと、「検査したように見えて実際には何も検査していない」経路が次のとおり見つかった。

1. **空のコーパス** — 文書が 0 件でも、error が 0 件なので exit 0。
2. **設定の打ち間違い** — `config.Load` は `yaml.Unmarshal` だけで、`referencs:` のような未知キーは
   黙って捨てる。利用者が有効にしたつもりの検査が無効のまま通る。
3. **明示した `dir:` の不在・大文字小文字違い** — 自動探索はディスク上の綴りを照合する
   （`matchesOnDiskCase`）が、`dir:` や `--dir` を書いた時点で探索ごと飛ばされ、存在確認すらしない。
4. **パターン外のファイル** — `parse.Dir` はファイル名パターンに合わない `*.md` を `continue` で捨てる。
   `ADR-1.md` や `draft.md` と名付けた記録は、どの検査にも現れない。
5. **Claude Code の hook** — `scripts/docdag-validate.sh` は `jq` や `docdag` が無いとき、
   docdag が exit 3（設定を読めない）で終わったときに exit 0 を返していた。hook の exit 1 は
   Claude Code では非ブロッキングで、exit 0 はそもそも何も伝えない。編集が設定を壊しても、
   エージェントはそれを知らない。
6. **ルールそのもの** — ルールを足してテストを書き忘れても、何も落ちない。0004 の層 3 は利用者の
   コーパスについて「沈黙しているルールが発火しうるか」を問うが、DocDag 自身の組み込みルールについて
   同じことを保証する仕組みは無かった。

どれも「exit 0 = 検査に合格した」という読み方を裏切る。CI の緑やエージェントへの無反応が
「検査が走らなかった」ことと区別できない限り、DocDag の強制力は保証できない。

## 決定

**検査が成立しない状態は、成立した検査の合格とは別の終了コードで失敗させる。** 具体的には次を行う。

1. **空のコーパスは exit 3。** 読み取り系のコマンド（`validate` / `lint` / `query` / `resolve` /
   `stats` / `export` / `context`）は、管理対象の文書が 0 件なら `model.ErrEmptyCorpus` で失敗する。
   メッセージには走査した Markdown の件数と `dir:` を確認せよという指示を含める。判定は各コマンドではなく
   共通のコーパス読み込み（`loadCorpus` / `loadCorpusAt`）に置く。`docdag new` は対象外とする。
   最初の 1 件を作るのは正当な操作だからである。
2. **`docdag.yaml` は厳格にデコードする。** goccy/go-yaml の `DisallowUnknownField` を使い、
   未知のキーは深さを問わず行番号付きで `ErrInvalidConfig`（exit 3）にする。`structural:` に書かれた
   ルール名が組み込みの検査名に無い場合も `Config.Validate` で拒否する。
3. **明示した `dir:` は、存在し、かつディスク上の綴りと一致しなければならない。** `dir:`・`--dir`・
   `kinds[].dir` に対して存在確認と大文字小文字の照合を行う。絶対パスでもコーパスの基点の配下にあれば
   相対化して照合し、基点の外は存在確認だけにする（Windows の一時ディレクトリに含まれる 8.3 短縮名
   `RUNNER~1` は `ReadDir` に現れないので、ボリュームのルートから照合すると誤検出になる）。
4. **パターン外の `*.md` は `unmanaged_file`（既定 warn）として報告する。** 文書としては数えず、
   グラフの節点にもしない。`README.md`・`index.md`・`template.md`（大文字小文字を問わない）、
   `template:` に指定したファイル、`_` か `.` で始まる名前は除外する。`structural:` で error に上げられる。
5. **hook は予期しない失敗を exit 2 で返す。** docdag が 0/1/2 以外で終わったら、docdag の stderr を
   そのまま添えて exit 2 にし、Claude Code に編集をブロックさせて理由を読ませる。`jq` や `docdag` が
   無いときは、プラグインだけが入った環境を壊さないために非ブロッキングのままにするが、
   「強制は OFF である」と明示する。
6. **全ルールに「発火する fixture」があることをテストで保証する。** `config.StructuralRules()` と
   `config.PresetRules()` で組み込みルールを列挙し、`cmd/rulecoverage_test.go` がそれぞれについて
   少なくとも 1 件の所見が出る fixture を実行する。対応表に無いルールがあればテストが
   `rule %q has no fixture that makes it fire` で落ちる。ルールを足してその発火例を書き忘れることは、
   CI で検出される。

終了コードの意味は既存の契約のまま使う。0 は検査に合格、1 は所見あり、2 は使い方の誤り、
3 は設定や入出力の問題で検査が成立しなかったこと。今回の変更は、これまで 0 に潰れていた
「検査が成立しなかった」状態を 3 に戻すものである。

## 根拠（調査結果・出典）

- **実測（本リポジトリ）** — 上記の CI 事故。`validate` は `OK: 0 docs` で exit 0、失敗したのは後段の
  手書き検査だった（GitHub Actions run 36310550548）。
- **実測（利用リポジトリ）** — 変更後のバイナリを Alt（989 件）・Plecto（117 件）・MatrixWhale（18 件）・
  modal-one（3 件）に当て、いずれも exit 0 のままであることを確認した。3 リポジトリは `template.md` を
  `template:` 未設定で ADR ディレクトリに置いており、これが `template.md` を既定で除外する理由になった。
- **ESLint** は、パターンが 1 件にも一致しないことを既定でエラーにし、許容するには
  `--no-error-on-unmatched-pattern` を明示させる。
  <https://eslint.org/docs/latest/use/command-line-interface#--no-error-on-unmatched-pattern>
- **goccy/go-yaml** の `DisallowUnknownField` デコードオプションは、構造体に無いフィールドを
  位置付きのエラーにする。<https://github.com/goccy/go-yaml>
- **Claude Code hooks** では、exit 2 だけがツール呼び出しをブロックし、stderr がモデルに渡される。
  exit 1 を含むそれ以外の非 0 は非ブロッキングのエラーとして扱われる。
  <https://code.claude.com/docs/en/hooks>
- **typescript-eslint** のルールテストは、ルールごとに valid と invalid の両方のケースを要求する。
  「発火しないことしか確かめていないルール」は、壊れていても気付けないからである。
  <https://typescript-eslint.io/developers/custom-rules/#testing-rules>

## 検討した代替案

- **`--strict` フラグで opt-in にする。** 既存の挙動は変わらないが、今回の事故は「誰も strict を
  付けていない CI」で起きた。すり抜けを既定で許す限り、強制力の保証にならない。breaking release
  （v0.5.0）として既定で厳格にし、CHANGELOG に移行手順を書く方を採った。
- **空のコーパスを warn にする。** warn は exit 0 なので、CI の結果としては今と区別できない。
- **パターン外のファイルを error にする。** 既存の ADR ディレクトリには README やメモが普通に置かれる。
  既定で error にすると、導入初日に大量の偽陽性が出る。warn を既定にし、厳密にしたいコーパスは
  `structural:` で error に上げる。
- **パターン外のファイルを文書として数える。** 実装の途中で一度そうなり、`OK: 3 docs` のように
  件数が水増しされた。件数は「検査した文書の数」でなければならないので、節点にも件数にも入れない。
- **文書単位の抑制コメント（`docdag:ignore`）。** v0.2 で却下した方針を維持する。
  抑制はすり抜けの経路を増やすだけで、この ADR の目的と逆向きである。
- **SARIF 出力で GitHub のコードスキャンに載せる。** v0.2 で却下済み。強制力の問題は出力形式ではなく、
  検査が成立したかどうかを終了コードが区別しないことにあった。

## 影響とトレードオフ

- **得るもの** — exit 0 が「検査が成立し、合格した」ことだけを意味するようになる。CI の緑と hook の
  沈黙を、そのまま信頼できる。
- **breaking change** — 設定に打ち間違いを抱えたまま動いていた利用者、`dir:` の綴りが違う利用者は、
  アップグレードした時点で exit 3 になる。いずれも以前から検査が効いていなかった状態が表に出るだけだが、
  移行の手間は利用者が負う。
- **ディスクアクセスの増加** — `dir:` の照合で親ディレクトリを `ReadDir` する。文書の読み込みに比べて
  無視できる。
- **hook の沈黙が残る場合** — `docdag` がインストールされていない環境では、hook はブロックしない。
  「強制が OFF である」ことはメッセージで伝わるが、強制そのものは CI 側に頼ることになる。
- **ルール網羅テストの維持費** — 組み込みルールを足すたびに、発火する最小の fixture を 1 つ書く必要がある。
  これは意図した負担である。
